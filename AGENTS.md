
# App design and implementation guidelines

> This file is loaded into the main agent's instructions every time the app starts (`session.js`, section `agentsGuide`; subagents get it when given the `agentsGuide` context section). Keep it accurate and reasonably short: everything here costs context on every reply.

## Product intent

This is a self-forming personal app: people describe what they need and shape the app through conversation. The audience is not necessarily technical. Do not present it as primarily an IDE, terminal, or developer dashboard.

- Use plain, friendly language. Describe outcomes rather than implementation details.
- Self Forming has one main surface: the chat (it opens directly, no Home screen), plus Settings and the conversation tree. There is no file explorer, terminal, voice mode, developer screen or activity view; do not add them back unless the user explicitly asks.
- Keep the agent's thoughts and tool calls visible in the chat as quiet, collapsible rows. Sign-in and model choice live in the in-chat Settings. App recovery lives only in Android Settings (gear in App info).
- Use examples as possibilities, not claims that unimplemented features already exist.
- Never submit a message, replace a draft, or make destructive changes just because someone selects a suggestion or opens a view.

## Visual direction

Quiet, neutral and text-first: one flat paper colour, dark ink, monospace type, hairlines and no animations on screen changes. The welcome view is a masthead (SELF FORMING), one invitation line and the credit ("Powered by" + a dotted-underlined pi-durable link). All views must belong to the same app. the look plugin and the plugins' CSS are the source of truth; when they change on purpose, update this section.

- Flat paper background (`--paper`, `--paper-bg: none`) on the page, the chats drawer and the settings dialog alike; other surfaces are transparent over it or a light card (`--surface`).
- Fonts: system monospace only (`--serif` and `--garamond` both resolve to "Courier New", "Liberation Mono", "Droid Sans Mono", monospace; `--mono` for code). Nothing is loaded from the network. The bundled Baskervville/EB Garamond files in `fonts/` are currently unused.
- Palette (tokens in `:root` of the look plugin `plugins/look-public/web/look.css`; do not invent per-view colours): paper `#f6f6f3` · light/surface `#fbfbf9` · ink `#282826` · brand (masthead) `#4a4a45` · muted `#676761` · accent `#30302e` · border `#bdbdb6` · error `#9e3b2c`. No shadows (`--shadow-*: none`).
- Shapes: small radii for cards, menus and the composer (4–12 px); the Send button and the jump-to-latest button are the only round controls (same size `--send`, same 25 px arrow, stroke 1.8, round caps). Send is filled `#30302e` with a light arrow; jump-to-latest is `--surface` with a hairline border and `--accent` arrow.
- Composer text: `clamp(15px, 4.2vw, 17px)`; message text 17 px.
- Do not use a grayscale filter over the app: it would alter user content as well as UI.
- Distinguish error/warning/selected states through wording, weight, underline and contrast—not colour alone.

## Navigation and headers

- Views occupy the full WebView viewport. No floating-card layouts.
- Header: no rule or border; the conversations (drawer) icon at the left (36 px target, `var(--muted)`). Settings opens from the model name in the footer (`#composer-model`, which clicks the hidden `#chat-settings`); keep `#chat-settings` because several modules listen to it.
- Attachments: the `+` in the composer opens a small row of two icon buttons (paperclip = files, picture = photos/images), each with an accessible label.
- Back is a flat chevron at the top LEFT (`.app-icon-button`, 36 × 36 target, no circle or border), inline SVG `viewBox="0 0 24 24"`, path `m14 6-6 6 6 6`.
- Title follows the back button: 24 px, weight 400, in the app font. Keep it short; explanations go in the view or a disclosure.
- Use accurate accessible labels and tooltips, e.g. “Back to chat”.
- Closing Settings or the conversation tree must not cancel an agent reply or reset a chat draft.

## Icons and controls

- Minimal inline SVG line icons, `currentColor`, rounded caps/joins, stroke 1.7–2.1. No emoji, raster icons or icon fonts.
- Icon-only buttons need an accessible name; decorative SVGs use `aria-hidden="true"`.
- **Secondary actions** (`.quiet-button`): transparent fill, 1 px `--border` hairline, 4 px radius, ink text at 16 px, 40 px tall; inside menus (`.chat-menu`) the border is hidden. Never pills.
- **Primary action** (at most one per view: Send, Save, Sign in): the dark accent fill (`--accent` / `#30302e`) with light text or icon. Disabled = reduced opacity, label kept.
- **Mostly square geometry.** Buttons, inputs, selects and the composer box use small radii (4–5 px); menus and cards up to 12 px. Round shapes are reserved for Send and jump-to-latest. No pill buttons.
- Settings shows controls, not essays: no long explanatory `settings-note` paragraphs; keep only live status lines (ids with `role="status"`) and errors. Empty notes are hidden by CSS.
- Form rows: muted label (15 px) above a full-width, regular-weight control (40 px tall). Focus = brighter border, not a double ring. Status chips are plain muted text.
- Toggle state uses `aria-pressed="true"` → underline, never a filled chip.
- Lists are flush rows: 40–44 px tall, icon/badge left, name, right-aligned muted metadata (size, count, chevron). No per-row cards or rounded row backgrounds; hover/selection uses the Surface colour.
- Minimum touch target 40 px for dense toolbars/lists, 44 px elsewhere.
- Inputs and selects: Surface fill, hairline border, 4 px corners, at least 16 px text on mobile.
- Show a visible focus outline and respect reduced-motion preferences.

## Layout and content

- Spacing scale: 4, 8, 12, 16, 24 px. Prefer 8/12 inside toolbars and lists.
- Monospace everywhere (`--serif`/`--garamond` for prose and controls, `--mono` for code, paths and sizes). Code blocks are bordered `--surface` cards (10 px radius) that scroll horizontally.
- Status/help text appears only when it carries information (errors, empty states). Don't permanently explain the obvious.
- Preserve room for actual content. Technical explanations belong in disclosures.
- Keep narrow screens, landscape, the Android keyboard, long filenames, empty and error states usable.
- Do not add extra safe-area/keyboard offsets when the host already sizes the WebView.

## Source and styling architecture

- Inspect the current editable source path with `app_update(info)` before editing the app. Do not assume a version-specific directory will remain current.
- The current app uses plain browser JavaScript modules, HTML and CSS. No framework, npm dependency, compiler, or build step is needed for app changes.
- Bundled upstream Pi/native modules are fixed. Use their existing APIs; do not invent host capabilities.
- Styles live where the screen lives (T2). `apps/common/app.css` is only the shared base: reset, page layout, typography and shared controls (`.quiet-button`, form rows, lists, dialogs), with no edition-specific values. Every UI plugin ships its own CSS (`plugins/<id>/web/*.css`: core-chat, core-conversations, the Settings section owners, the dev tools) and lists it under `styles` in its `plugin.json` (`{href, order?}`); `scripts/gen-builtins.sh` bundles those files in the generated `apps/common/builtin-styles.css` (`@import`s, sorted by order then id), which `index.html` links right after `app.css`, so the first paint is styled and the page looks right even when plugin composition fails; at run time the same files are the plugin's `styles` contributions (`plugin-styles.js` does not link bundled ones twice; installed plugins' CSS is linked after both sheets). Edit or delete rules in place in the owning file; do not add override layers. Shared widgets that several plugins use belong in `app.css`; keep them free of colours (use the tokens).
- No dark theme.
- Reuse and extend shared classes instead of copying styles into each view. Check specificity so feature selectors cannot accidentally override common controls.
- Preserve existing IDs, listeners, authentication, drafts, storage keys, and file safeguards when changing markup.

## Self-modification (read this before changing the app)

The app is meant to be reshaped. The original plain monospace look is deliberately plain: a neutral starting point that invites the user to bend the design language as they please, not a brand to protect.

- When the user repurposes the app (a recipe book, a trip planner, a shop counter…), change its visual identity and design style with it: palette, typography, shapes, density, iconography, masthead, invitation and wording should fit the new purpose. Do this in the look plugin's tokens (`plugins/look-*/web/look.css`) first, then in the plugins' components, and update the “Visual direction” section of this file so later agents follow the new style instead of restoring the old one.
- Small requests (“darker title”, “round buttons”) are just that: change what was asked and keep the rest consistent.

Work as an orchestrator:
- The main agent always orchestrates: it talks with the user, splits the work, decides, integrates and verifies. It does not need to do every step itself.
- Use the `subagent` tool to offload work and to run independent parts in parallel to speed up development: e.g. `spawn` one subagent for research or a dependency setup, another for a separate module or a build, while the main agent keeps editing or talking with the user. Use `run` for focused one-shot steps. Pick a cheaper model for simple work, give each subagent only the tools and context sections it needs, and a precise, self-contained goal with clear “done” criteria.
- Give parallel subagents separate files or folders so they do not overwrite each other; the main agent merges and reviews their results, checks them, and is the only one that calls `app_update apply` or `app_install_apk`.

Two layers, two paths:

| Change | How | Survives a new APK? |
|---|---|---|
| Web layer (JS/HTML/CSS) | edit `sourcePath`, then `app_update apply` | only if copied to `apps/common` before the APK is built |
| Native (Kotlin, permissions, host modules, `library/`) | follow `skills/self-rebuild/SKILL.md`, build, `app_install_apk` | yes |

Web-layer loop:
1. `app_update info` → `sourcePath` (today `<workspace>/.self-forming/app/<hostVersion>`). Edit there. New files are fine: every file in the folder goes into the revision and is served (only `native-host.js`, `library/`, `app-manifest.json`, `app-source-README.md` and the fixed fonts are refused).
2. Check the edits (there is no Node/Bun: read diffs carefully, grep for leftovers, keep `[hidden] { display: none !important; }` in mind when giving elements a `display`). Then call `app_update apply` alone as the last tool call. Once its successful tool result is durably saved, the session queues the revision, closes the harness and reloads the page. `apply` ends the turn (`control.terminate`, so nothing is in flight and the reload is immediate). Other conversations and subagents can still be busy; their unfinished durable work resumes after reload. The applying conversation then receives one follow-up input ("[app updated to <revision>; startup OK. You can continue working.]", or "… failed to start; the previous revision <x> was restored.") and simply carries on with its work, e.g. the next incremental change the user can watch. The user never has to background the app; if they do, that is a bug (see below).
3. Report what changed and what was not verified on screen.

Keep the repository in step (this is how descendants inherit changes):
- The live `sourcePath` and the repository are separate copies, and the web layer is two trees: `apps/common/*` (flat) and the built-in plugins `plugins/<id>/web/**`, which appear in `sourcePath` as `builtin/<id>/web/**` (`app_update` accepts subdirectories: ≤ 256 files, 4 MiB per file, 16 MiB per revision). After changes the user wants to keep, copy them back with `scripts/sync-builtins.sh from-live <sourcePath>` (and `to-live` to push the repository state into `sourcePath`; both remove nothing else than stale app files). Manifests (`plugin.json`) are not in `sourcePath`: edit them in the repository, run `scripts/gen-builtins.sh`, and copy `apps/common/builtin-plugins.js`. The APK and its embedded `source.zip` are built from `apps/common`; anything left only in `sourcePath` is lost for every rebuilt or descendant app.
- Commit with the user's own name and email (ask; never invent an identity).

Version masking:
- An applied revision wins over the APK's bundled web files for as long as the host version (`package.json` `version` = `versionName`) is unchanged. A new APK with the same version therefore keeps showing the old applied revision and hides its own web changes. Fix: merge the APK's changes into `sourcePath` and apply again, or bump the version when building.

How activation works (for debugging): `app_update apply` (`plugins/core-self-update/web/self-update-tools.js`) stages a revision and records its tool task, conversation and call IDs → the essential built-in `core-self-update` (`plugins/core-self-update/web/index.js`, C5; bundled copy if composition fails) keeps one `app-update-handoff.js` per session, observes commits through `host.harness.subscribeCommits` (cleared by the handle's `onStop`, ended by `onClose`) and matches the exact successful tool result and revision → a deferred `host.appRevision.onStaged` call (the session republishes its snapshot) → `app-revisions.js` `queue` → `app.js` `render` calls `applyQueued` → `activate` awaits actual session closure (`sessions.closeForReload`; sessions are opened by core-agent, C3d) → `app.activate` → `location.reload()`. Follow-up after the reload (`apps/common/app-update-followup.js`): `staged` writes the record `{revision, conversationId, taskId, callId}` to localStorage key `self-forming.app-update.pending` (never rename), `activate` adds `activated: true` after `app.activate`, and once the new session has read `app.info`/`app.ready`, `app.js` calls `deliverFollowUp`, which sends one input via `session.sendTo(id, text, {}, {whenBusy: "follow-up", requestId: "app-update:<revision>"})` (queued if that conversation is busy; the stable requestId stops a double delivery) and then clears the record. Neither global activity nor the selected conversation's busy state blocks a committed update. Closing interrupts active effects and preserves unfinished durable tasks; it does not wait for every agent to finish. Never call Session APIs directly inside a commit observer, and never activate on a timeout before storage has closed. Foreground, sign-in and UI-operation guards still apply. A race used to leave the revision queued until the next app reopen: `render` skipped it while an earlier empty `applyQueued` check was still in flight. Now the finishing check re-renders, and a 1.5 s retry runs while a revision is pending; keep both. If activation misbehaves again, add a temporary trace (e.g. append lines through the bridge method `workspace.write`) rather than guessing, and remove it afterwards.

Related tools:
- `manage_server` needs tmux and installs it with apt on first use (`plugins/core-servers/web/servers.js` `ensureTmux`). Ports may already be taken by other apps on the phone: check with curl before choosing one.
- Subagents: `run` helpers are one-shot; only `spawn`ed agents can receive later messages, and only by the name given at spawn (a title the user sets in the drawer is not that name). Tool names in the `tools` option are lowercase (`read`, `write`, `edit`, `bash`, …). Spawned subagents are listed under their parent in the drawer (busy dot while working); `archive`/`unarchive` hide an idle one under “Archived”, and `send` brings it back.

## Plugin architecture (0.5.0 foundation)

- Design: `docs/plugins.md`; authoring/build instructions: `skills/plugins/SKILL.md`. Plugins are trusted app code: no plugin authorization or approval dialogs. Existing Android permissions, secret scopes, destructive-data confirmations and APK-install confirmation remain intact.
- Built-in plugins are packages like installed ones: `plugins/<id>/plugin.json` + `plugins/<id>/web/index.js` (+ the implementation files that plugin owns, e.g. `core-providers-claude/web/provider.js`, `core-servers/web/servers-service.js`). Manifests carry `"builtin": true`, `essential`, `bundle`. The generated static registry `apps/common/builtin-plugins.js` (`scripts/gen-builtins.sh`, checked in; run it after changing any `plugin.json` or adding a plugin) imports every web entry, so start-up and the bundled fallback stay synchronous; built-ins never go through `plugins.install`. Shared engine modules stay in `apps/common`. Files are served as `builtin/<id>/web/**` next to the app files (not `plugins/`: `/assets/web/plugins/<id>/<hash>/` is reserved for installed plugins). Plugin sources import shared modules and `library/` by their served paths (`../../../session.js`, `../../../library/pi-ai.js`), so they only run in the served layout (web-lite/browser build, `tests/plugin-agent-support.mjs` `assembleApp`), not straight from the repository.
- Web composition: `plugin-bootstrap.js`, `plugin-runtime.js`, `plugin-builtins.js`, `plugin-client.js`.
  The built-in execution adapter uses ordinary service registration.
  Agent tools: plugins contribute pi-durable extensions (`agent.extensions`, `agent-extensions.js`, `ctx.pi`); per-conversation selection in Settings → Plugins. Core tools are essential built-ins (rows in their plugin folders, engine `core-agent-plugins.js`), merged into the permanent extension `self-forming-native`; never rename persisted extension/doc/task names. Prompt sections are the essential built-in `core-prompt` (extension `self-forming-prompts`; plugins add sections via their extensions). Skills: `agent.skills` contributions listed by the essential `core-skills` section; plugin skills live in `web/skills/<name>/SKILL.md` and are copied to `<workspace>/.skills/`. Failed core runtime copies fall back to bundled copies. The pi-durable `ExecutionEnv` is `plugins/core-execution/web/execution-env.js` (X1), offered as `execution@1` (`open(cwd?, {owner}?)`); core-agent opens session envs through it, app.js gives the bundled copy (`createExecution`) as fallback, and `native-host.js`'s `openNativeExecutionEnv` is only the last resort. Fetch is the essential built-in `core-net-native` (X4; `plugins/core-net-native/web/native-fetch.js`) providing `net.fetch@1` (a fetch function with `describe()`/`createFetch(host)`; core-agent gives it to the sessions and providers); the text workspace is `plugins/core-execution/web/workspace.js` (`workspace@1`); Claude sign-in is `plugins/core-providers-claude/web/claude-auth.js` (app.js: `loadClaudeAuth()`); each has the bundled copy as fallback and `native-host.js` as last resort. The conversation store is the essential built-in `core-storage` (X3) providing `storage@1` (`open({env})`: SQLite database "self-forming" over the bridge via `plugins/core-storage/web/native-database.js`, JSONL `/data/conversations` in the browser); core-agent opens each session store through it, app.js gives the bundled copy (`createStorage`). ChatGPT sign-in is `plugins/core-providers-chatgpt/web/chatgpt-auth.js` (X4b; app.js: `loadChatGPTAuth()`; its ID-token check uses the unmodified official `jose` 6.2.12 ESM build in `web/lib/jose/`, licence in `third-party/jose.LICENSE`); the bridge itself still comes from `native-host.js`. Servers are the essential built-in `core-servers` providing `servers@1` (`plugins/core-servers/web/servers-service.js`). Model providers are essential built-ins `core-providers-offline/-openai/-chatgpt/-claude` (contribution kind `agent.providers`, `agent-providers.js`; rows `plugins/core-providers-*/web/provider.js`, engine `session-providers.js`; the session engine is `session-engine.js` with `session-tail.js`, `session-threads.js`, `session-tree.js` (X6: in `plugins/core-conversations/web/`; X3b: the engine takes them from `conversations.engine@1` and the server binding from `servers.engine@1` while those plugins are active, the static imports being only the bundled copies listed in `docs/host-ownership.md`; `attachments.js` stays shared in `apps/common`), re-exported by `session.js`); the page session lifecycle is `core-agent` providing `agent.sessions@1` (`agent-sessions.js`, contract `agent-contracts.js`); its setup opens the sessions (`plugins/core-agent/web/open-sessions.js`, app.js only gives `sessionOptions`), and app.js uses the bundled core-agent copy when composition fails or is not ready within 5 s. Settings → Secrets is the essential built-in `core-secrets` (`plugins/core-secrets/web/secrets-settings.js`, `settings.sections` slot `secrets` → `#secrets-panel`; app.js mounts and wires the bundled copy; SecretStore/SecretBroker live in `plugins/core-secrets/native` (since 0.6.3, X5)). Settings → Background work is owned by `core-execution` (`plugins/core-execution/web/execution-settings.js`, slot `execution` → `#execution-panel`) and Settings → Plugins by `core-plugin-management` (`plugins/core-plugin-management/web/plugin-settings.js`, markup in `plugins-panel.js`, slot `plugins` → `#plugins-panel`); app.js mounts and wires the bundled copies, so the Plugins screen (the way to recover) works even when composition fails. Subagents are the essential built-in `core-subagents` (extension `self-forming-subagents`, `plugins/core-subagents/web/subagents.js`), built only from `host.harness` (agent.harness@1) and `host.pi` (A5). The chat is the essential built-in `core-chat` (C7a; `plugins/core-chat/web/chat.js` with `chat-renderer.js`, `chat-controls.js`, `attachment-composer.js`, `provider-settings.js`): it requires `agent.sessions@1` (session calls only through `sessions.current()`, providers through `providers()`/`providerLabel()`) and gets the page-owned parts (credential controllers, reloading, app-revision hooks, draft saving on close) from `chat-host.js`; app.js mounts the bundled copy when core-chat did not (composition failed, blocked, or past the 5 s deadline). The conversations drawer is the essential built-in `core-conversations` (C7b; `plugins/core-conversations/web/conversations.js`, on `agent.sessions@1`): app.js puts its nodes in place at load and wires the bundled copy when the plugin did not.
- Kotlin halves of built-ins live in `plugins/<id>/native/src` (+ optional `native/manifest.xml`), compiled statically into the APK by Gradle source sets (never dex-loaded); `apps/android` keeps only the host (MainActivity, NativeBridge routing, recovery, shared auth/secrets/store). Kotlin host: `plugins/core-plugin-management/native/src/.../PluginHost.kt`, SDK `apps/android/.../plugin/PluginApi.kt`; agent tool `plugins` uses `plugins.*` bridge calls. Compiler: `scripts/plugin.sh`; installable example: `examples/plugins/counter` (built-ins live in `plugins/`). Web runtime owns service dependency resolution; native host loads only the requested pinned native revision, not fictitious native service dependencies.
- Installed code is immutable and hash-identified, separate from editable workspace sources. Native revision changes require a process restart once code was attempted/loaded; web composition is page-owned. Never automatically retry a mutation after transport loss. Recovery can disable external plugins from Android Settings.
- Core plugin definitions and external packages share APIs but this is not a sandbox. Do not claim atomic rollback of arbitrary side effects or interruption of synchronous JS.
  Preserve active sessions when changing composition.

## Safety and checks

- Never display credentials or persist command input history to disk without an explicit requirement.
- Service secrets are configured only through Settings → Secrets. The native `SecretStore.kt` encrypts values with AES-256-GCM using non-exportable Android Keystore keys (some secrets need a fingerprint); app code never receives stored values, only commands get them through the execution environment.
- Never read or print the real key or stored credential values using agent tools. Never include them in app source, tests, console logs, transcripts, or error messages. Test only with generated temporary keys and clearly dummy values.
- Inject enabled secrets through execution `env` options, not command strings. Scope agent Bash and server access separately and default both to off. Existing processes retain inherited values; restart servers after changing credentials.
- Do not remove scope controls, damage checks, or explicit deletion confirmations.
- Heavy tests (real v86 emulation, headless Chromium, full `scripts/build-browser.sh` builds, the public-edition suite) are skipped unless `SF_HEAVY_TESTS=1` is set (`tests/heavy.mjs`; skip reason "heavy test: set SF_HEAVY_TESTS=1"). Do not run them on the phone.
- Check syntax, unique HTML IDs and stylesheet ordering before applying (no Node/Bun on the phone: review diffs and grep carefully).
- Static checks and mocked DOM tests are NOT visual verification. Say when on-device appearance or behavior remains unverified.
- Call `app_update(apply)` alone as the last tool call of a step after checking edits; the turn ends and the reload follows at once; the follow-up message after the reload says whether it started; then carry on (no need to report each step unless asked). Staging a revision is not proof it booted successfully.

## Rebuilding and updating the app on the phone

- The APK carries this repository (with `skills/` and its dedicated `.signing/`, but no Git history) as `assets/self-source/source.zip`. On first launch `SelfSource` unpacks it to `<workspace>/self-forming/` (never overwriting existing work; a missing `.signing/` or `skills/` is restored on every launch) and refreshes `dist/` (prebuilt web app, runtime payload, `source.zip`) from every newly installed APK.
- `./build-all.sh` uses the full Bun build when Bun and `node_modules` exist; otherwise `scripts/web-lite.sh` overlays `apps/common` onto the prebuilt `dist/app` (fixed modules such as `native-host.js` are reused, so `packages/native-host` changes need the full build). `scripts/pack-source.sh` then packs the source, and `build-apk.sh` signs with `.signing/` (the dedicated Self Forming key, v3, Android 9+; a rotation `lineage.bin` is used only if present, this fresh app has none). `./build-all.sh --release` builds the published non-debuggable variant with the same key (`outputs/apk/release/app-release.apk`); the default debug build is fine for on-phone rebuilds and updates in place either way.
- Install in place with the `app_install_apk` tool (only this package; Android asks the user). Bump `version` in `package.json` and `versionName` in `apps/android/app/build.gradle.kts` together, or editable-app revisions of the old version will mask the new UI.
- `.signing/` holds the private key and its password. It is gitignored. Never print it, commit it, or send it anywhere. Anyone who has the APK can extract it.
- Where things are on the phone, with `<workspace>` = /data/data/md.incept.selfforming/files/workspace (the session instruction `selfRebuild` states them, computed from the workspace path): source `<workspace>/self-forming`; signing key `<workspace>/self-forming/.signing/` (`self-forming.p12`, alias `self-forming`, password file `password`; used automatically by `build-apk.sh`); live web app source = `sourcePath` from `app_update` info (keep it in sync with `apps/common`); skill `<workspace>/self-forming/skills/self-rebuild/SKILL.md`; toolchain install log `<workspace>/.self-forming/toolchain.log`.
- The Android build tools (`pi-android install --accept-licenses`, licence accepted on the user's behalf; the welcome text says so while they are missing) start installing in the background when a native session opens (the self-forming-tools built-in `core-toolchain`, `plugins/core-toolchain/web/index.js`, providing `toolchain@1` from `agent.harness@1` onSession: nothing if `pi-android status` reports them installed or `flock` shows another install running; once per start, retried at the next start; never in the browser). Bump `selfFormingVersionCode` for every APK you install. The `app_install_apk` tool is registered only when the host reports `apkInstall`.
