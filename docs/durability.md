# App recovery

Applying an editable app revision first commits the `app_update` tool result, finishes the turn and closes the current Harness/SQLite owner before reloading. The next document opens the same saved conversation. A staged update interrupted before activation is not replayed automatically. Native **App recovery** restores code while retaining durable data and workspace files. See [editing the app](editing-app.md).

Starting with v0.7.0, Main remains the root conversation and **Fork into thread** creates a separate continuation through the upstream fork API. The active selection, conversation drafts and attachment references are stored alongside the durable session. Earlier context resets remain recorded, but the app no longer exposes a New chat reset shortcut. A task's saved `running` status does not prove a process is still executing. An assistant's aborted response may reflect interruption, explicit cancellation or another fault; only explicit tool interruption diagnostics are labelled as such. Upstream stores no complete crash/close/reopen event journal, so the inspector cannot reconstruct every lifecycle transition. Commit and document creation numbers are sequences, not wall-clock dates.

Pi Durable commits conversation state, task intent and tool results to the Android SQLite database. Opening the Harness recovers interrupted tasks but does not dispatch them until the application resumes it. In v0.3.0, reopening restored work behind the **Resume reply** button; v0.3.1 added automatic scheduler resume.

The app resumes pending work automatically on reopen, including background subagents and their result reporters. Model requests wait for the relevant ChatGPT or Claude account to be restored, or for sign-in. OpenAI API keys are not stored, so those requests wait for a key and **Resume reply**. Credential recovery retains the saved model and reasoning effort; it does not switch the pending work to the model selected in Settings. Missing credentials do not pause the durable scheduler or block server supervision. **Stop** cancels the selected run; stopped or completed work is not automatically started again. The local web app uses transient memory.

When the native host signals that the session should pause, the app closes the active Harness before transport cleanup can turn an interrupted model request into a terminal error. Closing seals task admission and signals interruption synchronously, then settles active tasks and storage. Returning to the foreground reopens the same SQLite conversation with a fresh execution adapter and resumes pending work. The bridge and authentication controller stay alive while the session is closed, including during external-browser sign-in. This does not reload the page or discard an unsubmitted draft. While agent work is active, the Android foreground service requests that the WebView remain running when the Activity is hidden.

The app also removes its `retry: { enabled: false }` override. Upstream Pi Durable 1.0.4 defaults to three retries of retryable model errors, beginning with a two-second delay. A retry checkpoint survives reopening. This matters when a connection fails before the host can signal that it is backgrounding. Permanent failures or exhausted retries still end a run; the UI now identifies a failed last reply instead of displaying "Ready when you are". Previous releases could already have committed such a terminal failure. Merely resuming the scheduler cannot undo it: ask the agent to continue that conversation once. The app does not fabricate another user message or requeue completed tasks.

Recovery continues the durable agent run, not a frozen shell process. The installed upstream 1.0.4 read, write, edit and bash tools use the default unsafe replay policy: a call interrupted after its intent was committed receives an interrupted result rather than being executed again automatically. The model can inspect files and decide what to do next. Completed tool results remain in the transcript.

New subagent calls use replay-safe durable receipts. An interrupted foreground call reuses its child conversation and submission. Background spawn/send calls cannot deliver the same input twice, and Stop records which prior submissions/reporters it is canceling so replay cannot cancel newer work. An older call already persisted with unsafe replay keeps that saved upstream policy; changing the tool registration does not revive a previously aborted call.

Managed servers launch only inside their durable task, including after reopen. A saved Stop request therefore takes precedence over restarting. Stop verifies that the owned tmux session disappeared, and failed cleanup stays pending for retry. A responding health endpoint without an owned tmux session is reported as a conflict rather than adopted as the requested server. This supervision resumes when the WebView Harness reopens; it does not run while the Harness is closed.

System guidance is assembled with native pi-durable context sections, recorded in `pi.system` entries. Subagents receive only their selected sections, with tool-specific guidance filtered against their actual tool set. Role and additional task instructions remain separate from these sections.

Native shell commands use a separate foreground execution service. Completed background launches can continue across tool calls, Activity recreation and ordinary background transitions; closing a conversation does not invoke cleanup on that service-owned environment. Pending tool calls remain cancellable. Process death, force-stop or reboot ends live shell processes; durable recovery can relaunch a managed command but cannot resurrect its memory. An unfinished model request may be issued again after recovery, and side effects completed before interruption cannot be rolled back.

Local regression tests use the real Pi Harness and SQLite to exercise server cleanup/restart, persisted Stop, subagent replay and delivery, credential waits, and named context sections. Model responses and execution commands are simulated; these tests do not establish physical-device process-kill, tmux/PRoot, or background-execution behavior.
